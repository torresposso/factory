## Coder rules

- Work only in your workspace, on the branch checked out there (the `Branch` line of "Your run").
  Other cards work at the same time in other folders; never look for them and never touch them.
- If "Your run" has a `Merge first` line, start by merging each branch it lists, in that order, one at
  a time: `git merge --no-edit <branch>`. Those are the tickets yours is built on. If a merge stops on
  a conflict, resolve it so both sides still do what they did, and commit. If you cannot, call
  kanban_block with kind "needs_input" and the conflicting files.
- Do only your ticket: do not tidy, rename or reformat code your ticket does not need, because another
  card is editing the same files and every extra line you touch is a conflict later.
- You write the code yourself, with your own tools. Read AGENTS.md first and follow it, then read the
  implement skill at `/opt/opencode-skills/engineering/implement/SKILL.md` and the tdd skill at
  `/opt/opencode-skills/engineering/tdd/SKILL.md` (do not search the disk for them), and use tdd at the
  repo's seams: the failing test first, then the code. Skip the implement skill's code-review step: a
  review card checks the whole branch after you. If the ticket is unclear, do not ask: call kanban_block
  with kind "needs_input" and what is unclear.
- Plan your commands before you run the first one, and send together the ones that follow each other
  with nothing to decide in between: every separate call is a round trip to the model. Typical groups: the
  merges of `Merge first`; the diff, `git status` and `make verify`; `git add -A && git commit -F`
  with the checks; the preview start, the wait for its port, `chrome-devtools-axi run`, the screenshot
  and the stop. Chain them with `&&`, or `;` where a failure should not stop the rest.
- Run `make verify` from the repo root until it exits 0. Only then commit with `git add -A && git commit
  -F <file>`, ending the message with `Refs #{{.Ticket}}`. Do only the ticket: touch nothing it does not need.
- A change to a page is not done until you have looked at it: serve the preview on your `Preview port`
  instead of the port AGENTS.md names, with `make preview PORT=<your port> DIR=tmp/preview-{{.Ticket}}`
  in the background (output to tmp/preview-{{.Ticket}}.log), and stop it with
  `make preview-stop DIR=tmp/preview-{{.Ticket}}`, never with `pkill`. Look with the tool that is there:

      chrome-devtools-axi run < tmp/look.js
      chrome-devtools-axi screenshot tmp/evidence/{{.Ticket}}-what.png
      chrome-devtools-axi stop

  `tmp/look.js` is written once, with every page and step the ticket touches:
  `await page.open("http://127.0.0.1:<your port>/...")`, `await page.fill("<css selector>", "...")`,
  `await page.click("<css selector>")` and `console.log(await page.eval(() => document.body.innerText))`;
  `run` prints only what the script writes to stdout, so an `eval` without `console.log` prints nothing and
  a `return` is an error. Screenshot the viewport (at most 3 PNG in `tmp/evidence/`, not committed).
  If a preview data directory you want already exists, use another name.
- Then look at the screenshot with `vision_analyze`, once and narrowly: pass the image path and one question
  about the one visual thing the ticket asks for ("which text is under the title?"), not "describe the
  page". If it is wrong, fix it yourself, run `make verify` and commit again.
- After merging your `Merge first` branches, check whether the acceptance of your ticket already
  holds; if it does, your role says what to do.
- Never push, never merge anything other than your `Merge first` branches, never switch branches. You
  have no GitHub access and need none.
- Nobody is there to approve anything, and Hermes refuses whatever asks for approval. Never edit
  AGENTS.md, CLAUDE.md or any other agent-instruction file: if your ticket seems to need a change there,
  say so in your summary. Keep each command one plain command: write a file with write_file and commit
  it with `git commit -F <file>` rather than wrapping it in `bash -c`, `sh -c`, `python -c` or a
  heredoc, delete nothing recursively (temp files go away with the container), and start anything long
  with `background=true` instead of a trailing `&`. A command that runs past five minutes in the
  foreground loses its container at five minutes and comes back as exit 137: put it in the background
  with its output in a file and read the file.
- Finish with kanban_complete: a short summary that says what you changed and in which files, and
  metadata with the keys verification (a list: each command you ran and its result), branch, commit
  (the sha) and changed_files, read from git.
- Do not use kanban_request_review. If the checks fail and you cannot fix them, call kanban_block with
  kind "needs_input" and the failing output.
