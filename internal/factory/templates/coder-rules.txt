## Coder rules

- Work only in your workspace, on the branch checked out there (the `Branch` line of "Your run").
  Other cards work at the same time in other folders; never look for them and never touch them.
- If "Your run" has a `Merge first` line, start by merging each branch it lists, in that order, one at
  a time: `git merge --no-edit <branch>`. Those are the tickets yours is built on. If a merge stops on
  a conflict, resolve it so both sides still do what they did, and commit. If you cannot, call
  kanban_block with kind "needs_input" and the conflicting files.
- Do only your ticket: do not tidy, rename or reformat code your ticket does not need, because another
  card is editing the same files and every extra line you touch is a conflict later.
- You do not write the code, run the checks or look at the page yourself: PiG does, in one call, and
  you check what it left. Plan your commands before you run the first one, and send together the ones
  that follow each other with nothing to decide in between: every separate call is a round trip to the
  model. Chain them with `&&`, or `;` where a failure should not stop the rest.
- Write the work order for PiG to `tmp/pig-{{.Ticket}}.md` with write_file: the ticket text from this
  card, exactly as it is, then a line with `---`, then this, with `<your port>` replaced by your
  `Preview port`:

      Read AGENTS.md first and follow it. Read the implement skill at
      /opt/opencode-skills/engineering/implement/SKILL.md and the tdd skill at
      /opt/opencode-skills/engineering/tdd/SKILL.md, and use tdd at the repo's seams. Do not run the
      code-review step. Do only the ticket above. If it is unclear, do not ask: stop and say what is
      unclear in your last message.
      When the code is done, run `make verify` from the repo root until it exits 0.
      If the ticket changes a page, look at it: start the preview in the background with
      `make preview PORT=<your port> DIR=tmp/preview-{{.Ticket}}` (output to tmp/preview-{{.Ticket}}.log),
      wait for the port, write `tmp/look.js` once with every page and step the ticket touches
      (`await page.open("http://127.0.0.1:<your port>/...")`, `await page.fill("<css selector>", "...")`,
      `await page.click("<css selector>")`, `console.log(await page.eval(() => document.body.innerText))`: `run`
      prints only what the script writes to stdout, so an `eval` without `console.log` prints nothing and
      a `return` is an error), then run
      `chrome-devtools-axi run < tmp/look.js`, `chrome-devtools-axi screenshot
      tmp/evidence/{{.Ticket}}-what.png` (the viewport, not the whole page; at most 3 PNG in that folder,
      which is not committed) and `chrome-devtools-axi stop`. Read the screenshot yourself and say
      whether the one visual thing the ticket asks for is right; if it is wrong, fix it and run
      `make verify` again. Stop the preview with `make preview-stop DIR=tmp/preview-{{.Ticket}}`, never
      with pkill. If a preview data directory you want already exists, use another name.
      Commit with `git add -A && git commit`, ending the message with `Refs #{{.Ticket}}`. Never push,
      never switch branches, never edit AGENTS.md, CLAUDE.md or another agent-instruction file. Your
      last message says what you changed, in which files, and what you ran.

- Then run PiG from your workspace, in the background, with `background=true`:

      pig -p --no-session --skill /opt/opencode-skills/engineering/implement --skill /opt/opencode-skills/engineering/tdd "Do the ticket and the work order on stdin." < tmp/pig-{{.Ticket}}.md > tmp/pig-{{.Ticket}}.out 2> tmp/pig-{{.Ticket}}.log; echo $? > tmp/pig-{{.Ticket}}.exit

  The work order goes in on stdin, byte for byte, so no quoting mangles it. `.out` takes PiG's last
  message, `.log` its diagnostics, and `.exit` appears when it ends, with its exit code. Wait for it
  with one command that returns the moment it ends, not with `sleep` calls of your own guessing:

      for i in $(seq 90); do [ -s tmp/pig-{{.Ticket}}.exit ] && break; sleep 3; done; cat tmp/pig-{{.Ticket}}.exit tmp/pig-{{.Ticket}}.out

  It gives up at 270 s, under the five minutes a foreground command has: if `.exit` is still missing,
  run it again.
- Then check what PiG left, in one call: `git log --oneline -5 && git status --short && make verify`.
  Its word is not the evidence; your own `make verify` is. If its exit code is not 0, `make verify`
  fails, or the work is half done, fix what is wrong with a second call of the same command and a
  shorter work order that says only what to fix (`cat` it into a new `tmp/pig-{{.Ticket}}-2.md`), once.
  If PiG says the ticket is unclear, call kanban_block with kind "needs_input" and its question.
- PiG commits as the work order says. If it did not, run `make verify` and, only when it exits 0,
  commit, ending the message with `Refs #{{.Ticket}}`. A review card checks the whole branch after you:
  yours cannot replace it.
- After merging your `Merge first` branches, check whether the acceptance of your ticket already
  holds; if it does, your role says what to do.
- Never push, never merge anything other than your `Merge first` branches, never switch branches. You
  have no GitHub access and need none.
- Nobody is there to approve anything, and Hermes refuses whatever asks for approval. Never edit
  AGENTS.md, CLAUDE.md or any other agent-instruction file: if your ticket seems to need a change there,
  say so in your summary. Keep each command one plain command: write a file with write_file and commit
  it with `git commit -F <file>` rather than wrapping it in `bash -c`, `sh -c`, `python -c` or a
  heredoc, delete nothing recursively (temp files go away with the container), and start anything long
  with `background=true` instead of a trailing `&`. A command that runs past five minutes in the
  foreground loses its container at five minutes and comes back as exit 137: put it in the background
  with its output in a file and read the file.
- Finish with kanban_complete: a short summary that says what you changed and in which files, and
  metadata with the keys verification (a list: each command you ran and its result), branch, commit
  (the sha) and changed_files, read from git and not from what PiG said.
- Do not use kanban_request_review. If the checks fail and you cannot fix them, call kanban_block with
  kind "needs_input" and the failing output.
